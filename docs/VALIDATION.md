## 备份与目录证据

- [Compose 恢复结果](compose-verification.json)：使用交付的 `scripts/backup.py` 创建备份并恢复到空数据库和媒体卷。19 张表计数与内容指纹一致；原图、缩略图、导出包可访问，原图及导出字节哈希相同；生成参数和个人状态一致；退出登录后原图返回 401。
- [独立 PostgreSQL 恢复结果](restore-verification.json)：另用 Windows PostgreSQL 17 的 pg_dump / pg_restore 核对所有表，并把媒体 tar 恢复到独立目录后核对原图哈希。
- [目录自动化结果](watch-verification.json)：图片在约 10 秒内被自动发现和分类，移走与重新放回后文件状态正确，资产数量仍为 1，源文件字节未被修改。测试 worker 的补扫间隔为 10 秒；产品默认 300 秒。该测试验证监控与补扫的组合行为，不把 Windows 挂载目录的文件事件可靠性单独宣称为已保证。

## 性能方法与边界

最终性能数据以 [限定资源 HTTP 基准](benchmark-compose-results.json) 为准。100,000 条合成资产、5 个并发登录用户，每组查询各 100 次计时采样，预热后计入鉴权、参数校验、SQL、前 60 条结果、总数、生成器分面和 JSON 序列化。每个查询均检查有实际命中结果，避免只测试空结果。

app、worker、PostgreSQL 绑定同样的 4 个逻辑 CPU（0–3）；内存上限分别为 4、1、10 GiB，总计 15 GiB。Docker 主机可用内存约 15.57 GiB。负载客户端在容器外，通过本机 HTTP 访问；这是 Windows Docker Desktop 上的受限 Linux 容器基准，并非另一台物理 Linux 服务器实测。

| 查询 | 每用户命中数 | P95 | 目标 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 生成器＋步数 | 20,000 | 239.63 ms | ≤ 1,000 ms | 通过 |
| 个人评分＋非收藏 | 6,000 | 188.82 ms | ≤ 1,000 ms | 通过 |
| Prompt＋模型＋CFG | 10,000 | 1,799.87 ms | ≤ 2,000 ms | 通过 |
| 完整 token＋否定词 | 50,000 | 944.84 ms | ≤ 2,000 ms | 通过 |
| 单个中文字符 | 50,000 | 342.57 ms | ≤ 2,000 ms | 通过 |

该基准检验十万条资产的查询性能，不包含十万张原图的导入时间、缩略图吞吐量、真实媒体磁盘容量、网络存储延迟或长时间稳定性测试。数据分布、硬件与并发量改变后应重新执行脚本。已提供可重复执行的合成数据和查询集合，参见 [开发文档](DEVELOPMENT.md)。

`benchmark-results.json` 和 `benchmark-compose-before.json` 为历史探索记录；旧评分分布导致个人条件没有命中资产，已标记为被替代，不能作为最终验收或同数据优化对比的依据。

## 首版边界

- ComfyUI 自定义节点和多分支只返回可靠的部分结果与告警，不推测未支持的节点语义。
- Prompt 权重与字典为有限规则集；生成器真实输出格式持续演进，需要后续扩充兼容样本。
- 测试包含一次受控备份恢复与任务租约恢复；尚未进行断电、磁盘损坏、数周运行或外部安全审计。
- pytest 当前有一条上游 Starlette 关于 TestClient 使用 httpx 的弃用提示，不影响测试结果。
- 视频、感知哈希、视觉分类与语义搜索不属于本次首版。
