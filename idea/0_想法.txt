问：
我需要一个本地和服务器都能运行的，网页界面的图片、视频整理和存储项目。我在用novalai或者本地的sd，以及未来的AI视频之后，需要有一个可以上传后自动读取其元信息，并且分类，还能通过复杂的搜索逻辑进行元信息内容搜索，以及一键复制元信息，自动对元信息进行分类的项目。除此以外我还没想到太多，你可以尝试在网上搜索类似的开源项目提取其优点整合进来。

答：
我查了一轮现有项目后，方向已经比较明确：你需要的并不是传统“相册”，而是一个面向 **AI 生成图片 / 视频的本地优先数字资产管理系统**。核心区别在于：**Prompt、模型、LoRA、Seed、Sampler、工作流等生成元信息必须是一等公民，而不是藏在 EXIF 面板里的附属信息。**

下面先给你一版可以直接继续往 PRD / 技术设计推进的总体方案。

# 1. 产品定义

暂定项目代号：**GenMedia Vault**

产品定位：

> 一个 Local-first、Self-hosted、Web UI 的 AI 图片与 AI 视频资产管理系统，用于统一收集、解析、分类、搜索、整理、复用和追溯 AI 生成媒体及其生成参数。

主要面向：

- NovelAI 用户
- Stable Diffusion / AUTOMATIC1111 用户
- ComfyUI 用户
- Forge / WebUI 衍生工具用户
- Flux / SDXL 等模型用户
- 未来 AI Video 用户
- 本地大量保存 AI 图片、视频的人
- 希望保留 Prompt / Seed / Model / Workflow 并进行复用的人

系统原则：

1. 本地可运行
2. NAS / Linux 服务器可运行
3. 浏览器操作
4. 原始文件尽量不被修改
5. 元数据自动提取
6. 元数据统一结构化
7. 支持非常复杂的查询
8. 不强依赖云服务
9. 支持几十万乃至百万级资产
10. 对未来新的 AI 生成器保持扩展能力

# 2. 对现有项目的参考

## 2.1 Immich

Immich 是目前非常成熟的自托管照片/视频管理系统之一。

值得吸收：

- 优秀的 Web 图片流浏览体验
- 图片 + 视频统一管理
- 缩略图和预览图异步生成
- Hash 去重
- Album
- Tag
- Metadata Search
- CLIP 语义搜索
- Docker 部署
- 多用户
- 后台任务
- 用户自定义存储结构
- Folder View

Immich 当前甚至已经发展出支持 AND / OR 组合条件的新 Search API。

但它的核心设计仍然围绕普通照片，而不是 AI Generation Metadata。

因此：

**借它的媒体管理架构，不照搬它的数据模型。** :chatgpt-content-reference{index="0"}


---

# 2.2 Hydrus Network

Hydrus 对这个项目非常有启发意义。

它的核心思想不是：

> 文件在哪个文件夹？

而是：

> 文件有什么标签？

对于拥有数万乃至几十万媒体文件的人，它用 Tag 体系取代传统目录作为主要组织方式。

值得吸收：

- Tag First
- 一个媒体可以属于无限多个分类
- 不依赖物理文件夹分类
- 强大的标签组合查询
- 本地优先
- 大媒体库设计
- 图片、视频甚至其他媒体统一处理

这是非常适合 AI 图片管理的思想。 :chatgpt-content-reference{index="1"}


---

# 2.3 digiKam

- Rating

并允许按这些维度搜索。

目前支持的元数据来源包括：

这证明：

我们的目标应该是做一个更加现代的 Web / Server / Video-capable 版本。 :chatgpt-content-reference{index="3"}

# 2.6 NovelAI 官方 metadata 工具

这里有一个非常重要的特殊点。

NovelAI 官方已经提供 metadata extraction 工具，并且当前 NovelAI 图片可能不只是普通 PNG text metadata，还可能把数据放在 alpha channel 中的 stealth metadata。

官方工具可以提取这些数据，并处理相关签名信息。

所以 NovelAI 解析不能只：

读取 PNG `tEXt`。

应该设计专门的：

`NovelAI Metadata Parser`

并兼容 NovelAI 官方的 metadata extraction 逻辑。 :chatgpt-content-reference{index="5"}

# 7. 元数据的三个层级

必须区分：

## Raw Metadata

永远保存原始读取值。

例如：

```json
{
  "Comment": "...",
  "parameters": "...",
  "workflow": {...}
}
```

---

## Normalized Metadata

转换成系统统一结构：

```json
{
  "generator": "novelai",
  "model": "...",
  "prompt": "...",
  "negative_prompt": "...",
  "seed": 123456,
  "steps": 28,
  "cfg": 5.0,
  "sampler": "...",
  "width": 1024,
  "height": 1536
}
```

---

## Derived Metadata

系统分析得出的数据：

```text
characters
style
artists
camera terms
quality tags
LoRA
IP Adapter
ControlNet
NSFW
orientation
aspect ratio
visual embedding
duplicate group
```

这样做极其重要。

因为：

**原始数据绝不能因为 parser 更新而丢失。**

之后 parser 升级可以直接：

```text
Raw Metadata
     ↓
Re-index
     ↓
New normalized metadata
```

而不用重新读取全部文件。

# 9. Prompt 不应该只是字符串

这是项目区别于普通 DAM 的关键。

例如：

```text
1girl, solo, white hair,
blue eyes,
<lora:abc:0.8>,
(masterpiece:1.2)
```

系统应该进一步解析成：

```text
Prompt Token
├── 1girl
├── solo
├── white hair
├── blue eyes
├── masterpiece
└── LoRA abc
```

并记录：

```text
token
weight
position
section
positive / negative
```

以后就能搜索：

```text
tag:"white hair"
```

而不是：

```text
prompt contains "white hair"
```

这个产品的核心对象是：


这就是它和 Immich / digiKam 最重要的区别。

# 59. 五个最值得优先做对的东西

如果开发资源有限，优先顺序建议是：

**第一：Metadata Parser Framework**

**第二：Normalized Metadata**

不同工具的参数必须映射到统一 Schema。

**第三：Search DSL**

**第四：Watch Folder**

**第五：Gallery + Metadata 快速复用**

找图 → 看参数 → 一键复制 → 重新生成。

形成闭环：

```text

   ↓

   ↓

   ↓
```

# 60. 产品最核心的一句话

这个项目真正解决的问题不是：

> “我的图片放在哪里？”

而是：

> **“我几个月前到底是用什么模型、什么 Prompt、什么 LoRA、什么参数生成那张图的，以及我怎样在几十万张生成结果里马上把它找回来？”**

整个产品和技术架构，都应该围绕这个问题设计。

这里面我认为有一个特别重要的判断：**不要基于 Immich 直接魔改，也不要把项目做成 A1111 的一个扩展。** Immich 的媒体基础设施非常好，但它的数据核心仍然是“照片”；A1111 Image Browser 又过度绑定单一生成器。你更适合独立做一个系统，然后通过 Parser、Watch Folder、API 与各类生成器连接。

另外，NovelAI 官方现在确实有专门的 metadata extraction 代码，包括从 alpha channel 中提取 stealth metadata，所以这一块最好直接按照官方逻辑做兼容，而不是只读 PNG 的常规文本字段。:chatgpt-content-reference{index="8"}

下一阶段最值得继续往下细化的是 **“数据库 Schema + 搜索 DSL + Metadata 标准化 Schema + 页面信息架构”**。这四块确定以后，基本就已经从“产品想法”进入可以正式开工的系统设计阶段。

问：继续

答：
这一阶段我会把前面的产品概念收敛成一套**可开发的系统设计 V0.2**。重点解决四件事：数据库怎么存、不同生成器的元信息怎么统一、复杂搜索怎么表达、前端页面怎么组织。

# 1. 本阶段目标

本阶段确定四个核心基础：

1. 数据库 Schema
2. Metadata Normalization Schema
3. Search DSL
4. Web 产品信息架构

这四项一旦稳定，前后端就可以开始并行开发。

# 41. Prompt 搜索语义

需要区分：

```text

```

全文包含。

以及：

```text

```

必须匹配解析后的完整 token。

```text

```

可能匹配：


```text
prompt.tag:"white hair"
```

只匹配：

```text
white hair
```

# 101. 下一步应进入工程设计

当前已经基本确定：

```text
产品边界

领域模型

Metadata 模型

数据库核心表

搜索模型

页面 IA

MVP
```

下一阶段应该正式进入：

```text
后端目录结构

具体数据库 DDL

Search DSL Grammar

Parser Plugin Interface

Job Queue 设计

文件扫描算法

Hash / Duplicate Strategy

REST API Schema

Docker Compose

前端路由

组件树

权限模型

部署方式
```

这会从：

“产品架构”

进入：

“工程架构”。

基于这一版，我建议有两个设计现在就锁死，不然后面返工成本很高。

第一，**Raw Metadata 永久保存、Normalized Metadata 可重建**。这样 NovelAI、ComfyUI 或其他生成器以后改格式时，升级解析器就可以重新索引，不需要依赖原始文件再次解析。

第二，**所有搜索入口统一成 AST**。简单搜索、筛选器、Smart Collection、DSL 都不要各写一套查询逻辑。它们最后都生成同一种 AST，再编译到 SQLite 或 PostgreSQL。这样以后增加 `CLIP 相似度`、`LoRA Weight`、`Workflow Node` 等查询条件，不需要重构整个搜索体系。

下一阶段我建议直接继续做**工程架构 V0.3**，我可以把 `具体数据库 DDL + Search DSL EBNF 语法 + Parser Python 接口 + FastAPI 目录结构 + Docker Compose 拓扑 + 前端路由/组件树` 一次性定下来。
